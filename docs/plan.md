| 산출물 | 배점상 위치 | 현재 |
|---|---|---|
| 공모전 기획서 (PDF) | 필수 제출 | **0%** |

코드는 돌아가지만 **성능 근거가 없습니다.** 평가 데이터셋이 없어 탐지율도 오탐률도
측정된 적이 없고, 룰 가중치(85/80/45/…)는 근거 없이 정한 숫자입니다.
실제 Claude 호출도 아직 한 번도 안 해봤습니다.

## 2. 무엇이 결과를 가르는가

**본선(내부 평가)** — 주제 적합성과 부적격 여부. 여기서는 화려함보다 **제출물이 제대로
갖춰졌는지**가 걸립니다. 양식 미준수, 출처 누락, URL 접속 불가가 실제 탈락 사유입니다.

**발표 심사(상위 11팀, PT 15분 + Q&A 5분)** — 여기서 무너지는 지점은 정해져 있습니다.

> "탐지 성능은 어떻게 되나요?" · "오탐은 얼마나 납니까?" · "룰 가중치는 왜 그 숫자죠?"
> "LLM이 틀린 안내를 하면요?" · "기존 은행 경고 문구와 뭐가 다릅니까?"

마지막 질문 빼고는 전부 **측정치**를 요구합니다. 지금은 하나도 없습니다.

→ **따라서 다음 작업은 기능 추가가 아니라 평가 체계 구축입니다.** 측정 없이 룰을 더
넣으면 지금까지처럼 감으로 쌓는 일이 반복됩니다.

## 3. 단계별 계획

각 단계는 **게이트**를 통과해야 다음으로 갑니다. 게이트를 못 넘으면 다음 단계를 시작하지
않고 범위를 줄입니다.

### Phase 0 — 전제 검증 (8/11 ~ 8/13, 3일)

기획서의 문제 정의가 실제 근거 위에 서는지부터 확인합니다. "개입이 병목"이라는 제 주장은
아직 검증되지 않은 가설입니다.

- [ ] 피해 통계 확보 — 경찰청·금감원 연간 피해액, 건수, 연령대 분포
- [ ] **개입 실패 근거 확보** — 창구 직원 만류에도 송금한 사례 비율, 재피해율.
      근거가 안 나오면 문제 정의를 바꿉니다
- [ ] 선행 서비스 조사 — 기존 앱·은행 경고가 무엇을 하고 무엇을 안 하는지 (차별화 논거)
- [ ] 대회 제공 양식 다운로드, 개인/팀 등록 상태 확정
- [ ] API 예산·키 확보, 배포 플랫폼 결제 수단 확인

**게이트**: 기획서 1페이지 문제 정의를 출처 있는 숫자로 쓸 수 있다.

### Phase 1 — 평가 체계 (8/14 ~ 8/19, 6일) ★ 가장 중요

- [ ] **평가 데이터셋 구축** — 합성. 저작권·개인정보 이슈 없음. 생성 방법과 근거를 문서화
  - 사기 시나리오 60건: 기관사칭 / 대출빙자 / 가족사칭 / 대면편취 / 원격제어 (수법별 12건)
  - 정상 금융대화 60건 — **오탐 측정용. 이게 없으면 탐지율만 높은 쓸모없는 모델이 됩니다**
  - 경계 사례 20건: 정상인데 위험 단어가 섞인 것 ("원격근무", "현금 인출 수수료")
- [ ] 지표 정의 — 탐지율(recall), 오탐률(FPR), 단계 분류 정확도, p95 응답시간, 건당 비용
- [ ] 평가 러너 (`eval/run.py`) — 세 구성 자동 측정: 룰 단독 / LLM 단독 / 하이브리드
- [ ] 베이스라인 측정 및 기록

**게이트**: 세 구성의 수치를 표로 제시할 수 있다. → **이 표가 발표자료의 핵심 슬라이드입니다.**

### Phase 2 — 성능 개선 (8/20 ~ 8/26, 7일)

여기서부터 데이터를 보고 고칩니다.

- [ ] 실제 Claude API 호출 검증 (현재 전부 스텁)
- [ ] `effort` 스윕 — low/medium/high/xhigh 품질·비용·지연 비교, 근거 있는 기본값 확정
- [ ] 룰 가중치 **재산정** — 데이터 기반. 현재 값은 전부 재검토 대상
- [ ] 오탐 잡기 (경계 사례 20건 기준), 룰 커버리지 확장
- [ ] 프롬프트 반복 개선
- [ ] 하이브리드 중재 규칙 재검증 — "룰이 하한"이 실제로 더 나은지 데이터로 확인
- [ ] 장애 주입 테스트 — 키 무효화·타임아웃·레이트리밋 시 폴백 동작 확인

**게이트**: 탐지율·오탐률이 목표치 도달, 베이스라인 대비 개선폭을 수치로 제시 가능.

### Phase 3 — 배포·안정성 (8/27 ~ 8/31, 5일)

심사 기간 접속 불가 = 결격. 가장 큰 단일 리스크입니다.

- [ ] 실제 배포 (슬립 없는 유료 인스턴스), 도메인 확정
- [ ] 헬스체크 + 외부 모니터링 (다운 시 알림)
- [ ] 부하·동시성 테스트, 레이트리밋·타임아웃 설정
- [ ] 접근성 점검 — 고령층 대상: 대비비, 글자 크기, 터치 영역, 스크린리더
- [ ] 모바일 실기기 확인

**게이트**: 72시간 연속 무중단 + 외부망에서 접속 확인.

### Phase 4 — 제출물 (9/1 ~ 9/5, 5일)

- [ ] 공모전 기획서 (제공 양식) — 문제 정의 → AI 해결방안 → 서비스 기획 → MVP
- [ ] 기능 명세서 (제공 양식) — `docs/api-spec.md` 확장
- [ ] 데이터 출처·라이선스 명시 확인
- [ ] PDF 변환, 양식 준수 최종 점검
- [ ] 데모 시나리오 준비

**게이트**: 9/5까지 PDF 완성. **9/6~9/7은 예비일 — 마감일에 작업하지 않습니다.**

## 4. 리스크

| 리스크 | 대응 |
|---|---|
| 심사 기간 접속 불가 → **결격** | 슬립 없는 인스턴스, 외부 모니터링, 룰 전용 폴백(이미 구현) |
| 주제 중복 (보이스피싱은 인기 주제) | "탐지"가 아닌 "개입·골든타임"으로 차별화. Phase 0 선행조사로 논거 확보 |
| 성능 근거 부재로 Q&A에서 무너짐 | Phase 1이 이것 하나를 위한 단계 |
| LLM 비용 초과 | effort 하향, 캐싱, 룰 전용 폴백 |
| 문제 정의가 근거 없이 무너짐 | Phase 0 게이트에서 조기 확인 — 늦게 발견할수록 치명적 |

## 5. 원칙

1. **측정 후 개선.** 데이터 없이 룰·가중치를 추가하지 않습니다.
2. **게이트 우선.** 못 넘으면 다음 단계로 안 가고 범위를 줄입니다.
3. **오탐을 탐지율만큼 본다.** 허위 경보는 다음 경고를 무시하게 만듭니다.
4. **마감일에 작업하지 않는다.** 9/5 완료, 이틀 예비.
5. **안전 관련 문구는 출처 확인 후 사용.** 잘못된 긴급 안내는 안내가 없는 것보다 해롭습니다.
